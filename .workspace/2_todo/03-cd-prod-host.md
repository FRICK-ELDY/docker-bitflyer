# ToDo: 本番ホスト向け CD を組み込む

対応する前段: [02-ci-github-actions.md](../3_archive/02-ci-github-actions.md)

ステータス: 未着手。**CI（02）が緑で運用できる状態になってから**着手する。

目的は、承認済みの成果物を **本番PC（単一ホスト・Compose）** へ安全に届け、入れ替え後も資金を守る経路を文書と手順で固定すること。PR ごとの自動実弾デプロイはしない。

作業は上から順に行う。前の完了条件を満たしてから次へ進む。

## 前提

- [Vision の本番環境](../0_doc/vision.md) と [env/prod.md](../0_doc/architecture/env/prod.md) を正とする
- 本番は VLAN1 の本番PC。作業用PC から監視・デプロイする
- CI で format / compile / test が通っていること
- 本番 API キー・Webhook 等はホスト側シークレットのみ。Git・イメージ・CI ログに出さない
- 初回 CD の検証は `dry_run` または発注停止状態で行う。`live` 解禁は別判断

## 手順

### 1. 文書に CD 方針を書く

- [ ] `architecture/ci-cd.md`（CI で作っていなければ新規）または `env/prod.md` に CD の流れを追記する
- [ ] 配布の形を固定する: **CI が本番用イメージをビルド → コンテナレジストリへ push → 本番PC が pull して Compose で入れ替え**
- [ ] トリガーを固定する: `main` へのマージだけでは実弾を動かさない。明示タグ（例: `v*`）または手動承認を必須にする
- [ ] ロールバックの単位（前イメージタグへ戻す）を一文で書く
- [ ] VLAN3 → VLAN1 の到達は最小ポートのみ、と Vision の Least privilege に合わせる旨を残す

完了: 「何が成果物で、誰がいつ本番を更新するか」が文書だけで説明できる。

### 2. 本番用イメージを定義する

開発用 `Dockerfile`（bind mount・`mix phx.server`）とは分ける。

- [ ] 本番用 `Dockerfile`（例: `Dockerfile.prod`）を追加する
- [ ] `MIX_ENV=prod` の release（または同等の本番起動物）をビルドする
- [ ] ソースの bind mount に依存しない。実行に必要なものだけイメージに入れる
- [ ] assets の minify / digest が release に含まれる
- [ ] イメージに `.env`・API キー・`SECRET_KEY_BASE` を焼かない
- [ ] ベースの Elixir / OS バージョンを CI・開発と大きくずらさない（ずらすなら文書に理由を書く）

完了: ローカルまたは CI で本番用イメージがビルドでき、コンテナ単体で起動コマンドが定義されている。

### 3. 本番用 Compose を置く

- [ ] `compose.prod.yaml`（名前は任意。開発用 `compose.yaml` と混線しない名前）を追加する
- [ ] サービスは開発と同じ境界（`app` / `db`）を維持し、接続先・再起動・公開面だけを本番向けにする
- [ ] ホストへの公開は最小（管理 UI / DB を不用意に晒さない）。`prod.md` と一致させる
- [ ] `db` は名前付きボリュームまたはホスト永続ディスク。バックアップ方針への参照をコメントまたは文書に残す
- [ ] `app` はレジストリのイメージタグを参照する。`:latest` だけに頼らない運用（タグ or digest）を決める
- [ ] `.env.example` に本番で使う名前を足す（値は入れない）。`TRADE_MODE` の本番既定は文書で明示する

完了: シークレットをホストに置いた前提で、Compose ファイルだけ見れば起動構成が追える。

### 4. CI からレジストリへ push する（CD の自動化部分）

- [ ] CI ワークフローに「本番イメージ build & push」ジョブを追加する（CI 本体の test ジョブとは分離してよい）
- [ ] レジストリは GitHub Container Registry（GHCR）を初期の正とする（変更するなら文書を先に直す）
- [ ] push の条件: 明示タグまたは `workflow_dispatch` / 環境保護ルール付き。全 PR では push しない
- [ ] イメージタグに git SHA または semver を含める
- [ ] GitHub Environments（例: `production`）でレビュー必須にできるなら使う
- [ ] レジストリ認証は GitHub token / OIDC 等。長期の個人 PAT をリポジトリに書かない

完了: 承認された参照から、追跡可能なタグのイメージがレジストリに存在する。

### 5. 本番PC 側の入れ替え手順を固定する

作業用PC から本番PC へ、次を手順書として残す（`prod.md` または運用手順の節）。

- [ ] 事前: ディスク残量、時刻同期、Docker 稼働、現行タグの記録
- [ ] デプロイ前: **新規発注を止める**（サーキットまたは運用操作）。可能なら未約定を把握する
- [ ] `docker compose -f compose.prod.yaml pull`（または同等）
- [ ] 入れ替え: `up -d` 相当。DB を不用意に消さない
- [ ] 起動後: ヘルス、ログ、内部状態と取引所の突合（`live` のとき）。不整合なら Ready にせず停止のままアラート
- [ ] 事後: 監視の心拍確認。問題なければ段階的に発注を再開（初回は厳しい上限）
- [ ] 失敗時: 直前タグへ戻す手順を同じ文書に書く

自動化するなら:

- [ ] 本番PC 上の更新スクリプト（pull → 停止ゲート確認 → up → ヘルス待ち）をリポジトリまたはホストに置く
- [ ] スクリプトは「発注停止の確認」なしに `live` を再開しない

完了: 人一人が文書どおりに追えば、作業用PC から本番を更新できる。

### 6. 安全装置と検証（実弾なしで先に通す）

- [ ] 本番相当の Compose を、キーなしまたは検証用・発注停止で一度上げる
- [ ] イメージ入れ替え後に UI / ヘルスが復帰することを確認する
- [ ] ロールバック（前タグ）が短時間でできることを一度試す
- [ ] Discord 等の通知があるなら、デプロイ開始・完了・失敗が届くことを確認する（アダプタ未着手ならログで代替し、後続に残す）
- [ ] `live` 解禁チェックリストを `prod.md` に短く置く（最小ロット、上限、監視到達）

完了: 実弾なしで「配る → 入れ替える → 戻す」が一度成功している。

### 7. README とアーカイブ準備

- [ ] `README.md` に本番デプロイへのポインタ（詳細は Architecture / 本 ToDo のアーカイブ）を書く。キーの置き方は書かない
- [ ] 開発用と本番用の Compose / Dockerfile の見分けを README か Architecture に一文で書く
- [ ] 完了後、このファイルを `.workspace/3_archive/` へ移す

完了: 新規運用者が「CI の次に CD で何が届き、本番で何をするか」を辿れる。

## 実装時の決めごと

- 初期は単一ホスト Compose。Kubernetes や複数ホストは対象外
- `apps/ui` と `apps/bitflyer` のリリース分割はしない（評価文書どおり、痛くなってから）
- watchtower 等の自動最新追従は、発注停止ゲートなしでは採用しない
- ペーパー取引や戦略本体はこの ToDo で作らない。配る箱と入れ替え手順だけを作る

## 完了の見方

- 本番用 Dockerfile と Compose がある
- 承認付きの経路でイメージがレジストリに載る
- 本番PC での pull / 入れ替え / ロールバック手順が文書化されている
- `main` マージ alone では実弾デプロイが走らない
- シークレットが Git・イメージ・CI ログに出ていない
- 実弾なしで一度、入れ替えとロールバックを確認している

- 複数環境への同時デプロイや Blue/Green の本格化（必要なら後続）
