## 観点別の総括

### 強い

**手数料会計の設計**。`Product.fee_currency/1` を単一の決定点にし、それを使う 3 経路（建玉 inventory / 残高説明 / realized PnL）を同じ分岐で書いた。買いの `held_size = size − fee`、反対売買・ドテンの減算も `held` 基準、`fee` の NULL / 0 / 記録済みの 3 状態を残高許容幅の設計に落とす——ここまで詰める個人プロジェクトは見たことがない。`+4` を付けた。

**fail-closed の一貫性**。`DailyLoss` の barrier / generation（`force: true` でも barrier を無視しない）、`BalanceCache.reapply_holds!`（絶対 put の上に hold を再減額し、足りなければ unsynced）、`Equity` の stale 方針を呼び出し元ごとに分ける（authorize は fail-closed / 周期 enforce は halt しない）。**どこに安全弁を置くかの判断がぶれていない。**

**live 起動ガード**。`LiveSafety` は 7 本の Risk 上限を env 必須にし、形式と上限（`max_open_age_ms` は 7 日）まで検証し、`FixedOnce` を禁止し、spot allowlist を強制する。`runtime.exs` は `TRADE_MODE` 既定 `dry_run`、`BITFLYER_LIVE_CONFIRM` は当日 UTC 日付一致。**「live 解禁が明示的か」の粒度が env の存在ではなく値の妥当性まで来ている。**

**moduledoc の質**。今サイクルは実装と同時に「なぜこうしたか」「何が残っているか」が moduledoc に入るようになった。`Risk` は probe→reserve の TOCTOU を自分で認め、`Reconcile` は両向き救済の意図を書き、no-op migration は「削除しないこと」の理由を 3 つ挙げる。**次の読み手（次サイクルの自分）に対する投資**として、これは実装そのものと同じくらい価値がある。

### 弱い

**「完了」の判定精度**。今サイクル最大の問題は実装ではなくプロセスにある。improvement-plan は P0 #1 に「実応答（または公式が単位を明記した fixture）で一致する」という完了条件を自分で書き、その条件を満たさないまま取り消し線を引いた。同じ表の中で完了条件と証跡が矛盾している。前回は「宣言 3 件に対し消化 0 件」で `-1`、今回は逆方向で `-2` である。

これは些細な文書の話ではない。**本評価の依頼文自身に「improvement-plan の『完了』は信じずコード確認」と書かれている**——前回サイクルで信頼が既に目減りしている証拠である。完了宣言に「条件を満たした根拠」を 1 行必須にし、書けないものは `部分完了` と残す。それだけで回路は元に戻る。

**反証の設計**。P0 #2 は「反証回帰」を目的に立てられたのに、ハーネスが本番と同じ手数料モデルを実装しているため、**自モデルが誤っている場合に全テストが緑のまま live で halt する**。固定できたのは「JPY 決め打ちからの逸脱」だけである。取引所の挙動はモックでは決まらないので、境界を「観測して記録する」側に移すしかない。

**診断ツールの副作用**。`mix bitflyer.game_day_stage2` は良い方向の一歩（SQL 代替の卒業、`after` での完全な後片付け）だが、`RiskState`（`name == "default"` の単一行、モードを持たない）を `Risk.clear_circuit()` で 4 回消す。paper でこのタスクを走らせると live 側の停止理由が消え、`CircuitSync` が次回起動で「停止していない」として復帰させる。DB を分けている限り事故にならないが、**停止理由の永続化という最も重い安全装置を診断タスクが無条件に解除できる**構造は直すべきである。あわせて `RiskState` がグローバル 1 行である設計判断は overview に書かれていない。

**入力が揃ったのに使っていない**。bid/ask を Cache に載せたのに、成行の残高拘束は LTP 基準のままである。`max_spread_pct` を通る板でも片側 0.25% ぶん過小に拘束しうる。金額は小さいが、この種の「取ったデータを使い切っていない」負債は次の機能で必ず表面化する。

## 比較軸

同種の個人製自動売買（多くは Python + 取引所 SDK + cron / systemd）と比べたときの位置は前回と変わらない。**上位数%**である。突合の両向き救済、HWM の永続化と単調性の DB 述語化、ETS の barrier / generation による Ready 化制御、`prep_stop` での drain と `submission_unknown` 化——これらは商用の執行基盤で見る種類の作り込みで、この規模の個人プロジェクトで揃っている例をほとんど知らない。

一方、商用と比べて明確に足りないのは 2 点である。

1. **取引所の実挙動を観測する層**。契約テストは公開 GET の corpus まで来ているが、private の非ゼロ約定（手数料の単位、部分約定の刻み、`getbalance` の反映遅延の実分布）は 1 件も観測記録が無い。商用ならここに「最小ロットで毎日 1 往復して差分を記録する canary」が常駐する
2. **ホスト外の観測**。率・推移がホスト外に残らず、ホスト死の検知が未配備。これは道具が揃っていて配備だけが残っている状態なので、コストは低い

## 結論

**純点 +15（+31 / -16）。live 実発注は依然不可。残条件は「別ホスト監視の配備」と「commission 単位の実観測（とくに売り側）」の 2 件。**

今サイクルは前回の指摘に対する応答として非常に質が高い。前回書いた改善方針がほぼそのままコードになっており、そのうえで moduledoc に残差まで書いている。実装力に疑いは無い。

問題は**「完了」という言葉の使い方**に移った。実装が揃ったことと、その実装が現実と一致していることの検証が済んだことは別である。P0 #1 の完了条件を自分で書いた側が、その条件に照らして落とす判定を実行しなかった。これは資金を扱うシステムにおいて、コードのバグより静かに効く種類の問題である。

次サイクルで上位 2 件（監視配備・実観測）を閉じ、完了宣言に根拠を添える運用に戻せば、live 最小ロットの解禁を止める技術的理由は無くなる。
