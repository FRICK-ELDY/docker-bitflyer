# 要望: Discord 通知（observe のアダプタ）

ステータス: 未着手。Umbrella の骨格（[01-bootstrap-umbrella-and-docker.md](../2_todo/01-bootstrap-umbrella-and-docker.md)）のあとに着手する。

## 背景

Vision は「異常時は人に届く。届かない監視は監視ではない」としている。  
Architecture の observe（ログ・メトリクス・ヘルス・アラート）の、人への到達経路として Discord を使う。

`apps/discord` は作らない。Discord は取引の正本ではなく、通知の出力先である。

## 確定した置き方

| 項目 | 方針 |
| --- | --- |
| 形 | `apps/bitflyer` 内の通知アダプタ（GenServer 等） |
| 監督 | 取引エンジンとは兄弟。通知の例外で発注側を再起動しない |
| 発注経路 | 通さない。通知の成否で注文を止めない・待たせない |
| 初期の送り方 | Incoming Webhook |
| 秘密情報 | Webhook URL は環境変数。Git・ログ・メッセージ本文に出さない |

```text
risk / executor / market-data / 起動突合
        │  イベント（停止、切断、不整合、復旧）
        ▼
   observe（ログは必ず残す）
        │
        ▼
   Discord adapter  ──Webhook──►  Discord
        │
        × 失敗しても発注経路には戻らない
```

## この要望で満たすこと

1. 人が見るべき事象を Discord に送れる
2. Webhook 未設定または送信失敗でも、取引は継続し、失敗はログに残る
3. 同じ障害の連投でチャンネルを埋めない（種別ごとにまとめる / 間隔を空ける）
4. メッセージから「今トレードしてよいか」と「何が起きたか」が分かる
5. Architecture の observe に、Discord はアダプタであると追記する

最初に送る事象（骨格が動いたあと、発注より前でも一部は試せる）:

- プロセス / コンテナの起動と停止
- サーキットオープン（取引停止）と、再開した場合はその旨
- 内部状態と取引所状態の不整合
- WebSocket 切断が閾値を超えたとき
- Discord 自身への送信失敗（ログのみ。通知の再帰はしない）

## メッセージに含めてよいもの / いけないもの

含めてよい:

- 環境（dev / prod）
- 事象の種別と時刻
- 停止理由の要約
- 対象銘柄（必要なとき）
- 「発注中 / 停止中」の現在状態

含めてはいけない:

- API キー、Webhook URL、署名
- 注文の完全なペイロード
- 残高や建玉の詳細を、必要以上に長く出すこと

## この要望でやらないこと

- `apps/discord` を Umbrella に追加すること
- Discord Bot、スラッシュコマンド、リアクションによる停止 / 再開
- Discord から注文すること
- 複数チャンネルの本格的な使い分け（後で必要なら設定で足す）
- Discord 障害を理由にした取引停止

Bot やコマンドで遠隔操作したくなったら、認証・権限・誤操作の評価を別要望にする。そのとき初めてアプリ分割を検討する。

## 完了の見方

- 通知モジュールが `bitflyer` にあり、発注経路から独立している
- 開発環境で Webhook を設定すると、起動または停止イベントが Discord に届く
- Webhook を外すと、アプリは落ちず、ログだけが残る
- 秘密情報がリポジトリと Discord 本文に出ていない
