# 要望: 戦略軸をトレンドフォローに固定する

ステータス: 方針確定。実装は live 解禁（improvement-plan P0）および paper 検証基盤の後。アルゴリズム高度化・パラメータ UI・revision canary は意図的に後回しのまま。

根拠: Vision（戦略の中身は後続バックログ） / [improvement-plan.md](../0_doc/evaluation/improvement-plan.md)（戦略高度化は縦貫通の安全化の後） / 2026-09-11 の戦略方針議論

## 背景

本システムは bitFlyer Lightning 上で 24/365 稼働する自動売買を目指す。利益指標は月利ではなく**年利（年次リターン）とドローダウン**で見る。

戦略の中身は Vision 時点では未定義だった。基盤側は `Bitflyer.Strategy` 契約と縦貫通用の `FixedOnce`（dry_run / paper）まであり、本番向けの売買仮説はまだない。

自動売買として候補に挙がった方針を比較し、**第一軸をトレンドフォローのみ**に決めた。他ファミリーは当面実装しない。

## 比較と採否

| 方針 | 採否 | 理由 |
| --- | --- | --- |
| トレンドフォロー（中低頻度） | **採用（第一軸）** | シグナルが単純で `evaluate/3` に載せやすい。取引回数が相対的に少なく、手数料・API 上限の影響が小さい。失敗モード（レンジでの連続損）が分かりやすく、halt / サイズ縮小と対話しやすい |
| ミーンリバージョン（短期） | 見送り | 高頻度寄りになりやすく、手数料・スリッページ・API レート制限が怖い。板・スプレッドゲート（improvement-plan P3）未整備の段階では不利 |
| グリッド / DCA | 見送り | 実装は単純だが、一方通行トレンドで在庫・含み損が膨らみやすい。年利の見た目が良くても実質は保有リスクの変形になりがち |
| アービトラージ / マーケットメイク | 見送り | 複数所・板本格購読・低レイテンシが必要。Vision の非目標・現行アーキと合わない |
| ML 予測 | 見送り | Vision でも非目標。リーク・レジーム変化で壊れやすく、基盤未成熟だと検証コストが大きい |

## 確定した置き方

| 項目 | 方針 |
| --- | --- |
| 戦略軸 | トレンドフォローのみ（当面、他ファミリーを混ぜない） |
| 評価の尺度 | 月利ではなく年次リターン + Max DD（複数レジーム） |
| 頻度 | 中低頻度（秒〜分の過剰評価や高回転は避ける） |
| 銘柄前提（初期） | spot（例: `BTC_JPY`）。FX レバは [fx-collateral-adapter.md](./fx-collateral-adapter.md) 完了後でも可 |
| モジュール境界 | `Bitflyer.Strategy` の `evaluate(market, positions, params)` → command 列。取引所 API / Executor は呼ばない（現行契約のまま） |
| 安全装置 | 利益機能より Risk（サイズ・DailyLoss・stale・halt）。戦略は「休場（何もしない）」を正規の行動とする |
| 検証順 | 仮説の文章化 → dry_run / paper（手数料込み）→ 極小 live → 段階拡大 |

```text
市場スナップショット（ticker 等）
        │
        ▼
  TrendFollow.evaluate  ──►  [command] または []（休場）
        │
        ▼
  risk-manager → order-executor
```

## トレンドフォローの骨格（初期仮説の枠）

実装パラメータは未確定。次を「戦略仕様の必須項目」とする。

1. **エントリー** — 方向が付いたら乗る（ブレイクアウト系、または移動平均系のどちらか一方から始める）
2. **エグジット** — 逆シグナル、またはトレーリング。固定幅の利確だけに依存しない
3. **サイズ** — 可能ならボラ（ATR 等）連動。固定ロットは検証初期のみ可
4. **休場** — スプレッド異常・データ stale・halt 中は新規なし

未決（仕様化するときに決める）:

| 項目 | 候補の例 |
| --- | --- |
| 時間足 | 15分 / 1時間 / 4時間 |
| 方向 | 当面ロングのみ（spot）か、両方向か |
| リスク予算 | 1トレード何%、年次・DD 上限何% |
| 指標ファミリー | ブレイクアウトか移動平均か（最初は1つ） |

## この要望で満たすこと

1. バックログと Vision 追随の文書として「戦略軸 = トレンドフォロー」が明文化されている
2. ミーンリバージョン・グリッド・裁定・ML を初期スコープ外とした理由が残っている
3. 実装着手時に、上記骨格と未決表を埋めた戦略仕様へ落とせる
4. improvement-plan の「戦略高度化は安全化の後」と矛盾しない着手順になっている

## この要望でやらないこと（初期）

- トレンド以外の戦略モジュールの並行実装
- パラメータ UI・revision canary・複数戦略の同時稼働
- 板本格購読前提の高頻度トレンド追随
- FX / レバレッジ前提のトレンド戦略（spot で仮説検証してから）
- 「毎月勝つ」ことを成功条件にすること

## 完了の見方

- 本ドキュメントの方針が、戦略仕様（別ドキュメントまたは本ファイル追記）と README / overview の記述と食い違わない
- 第一戦略が `Bitflyer.Strategy` behaviour を満たし、live 以外で縦貫通できる
- paper（または同等）で手数料込みの年次指標と Max DD を評価した記録がある
- 本番解禁は improvement-plan P0 完了後の判断であり、本要望の「方針確定」だけでは live 解禁しない

## 着手タイミング（推奨）

1. improvement-plan の **P0**（live 解禁前の穴）を閉じる
2. paper 経路で建玉・損益が追えることを確認する
3. 未決表（時間足・方向・リスク予算・指標）を埋めて戦略仕様を書く
4. `FixedOnce` とは別の TrendFollow 実装を dry_run / paper で検証する
